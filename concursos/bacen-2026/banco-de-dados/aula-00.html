Fluxo do projeto de BD

Requisitos → projeto conceitual (gera o MER) → projeto lógico → projeto físico (o SQL DDL gera o esquema físico).

Sinônimos que confundem

Alguns autores chamam o conceitual de "modelo lógico baseado em objetos" e o lógico de "modelo lógico baseado em registros". Os dois de maior abstração são o conceitual e o lógico (FGV).

Seus erros neste tema (Q13 e Q17)

  • Estruturas de armazenamento e métodos de acesso fazem parte do projeto FÍSICO, e não do lógico.
  • O modelo conceitual usa os requisitos de DADOS. Os requisitos de negócio geram as funcionalidades do sistema. Não é ele quem "aplica regras para evitar redundância" (isso é normalização, no lógico).
  • O modelo lógico não considera desempenho (Q14: E). Desempenho é assunto do físico.

Muito cobrado · foram 2 dos seus erros

Cada um no seu quadrado

Cada nível tem seu próprio registro, esquema e DDL: externo/externo/externo, conceitual/conceitual/conceitual, interno/interno/interno. O usuário acessa por uma DSL (sublinguagem de dados) = DDL + DML.

Mapeamentos

  • Externo/conceitual: ligado à independência lógica
  • Conceitual/interno: ligado à independência física
  • Externo/externo: um esquema externo criado a partir de outro
  • Mapeamentos = transformar requisições e resultados entre os níveis

Seus erros neste tema (Q21 e Q53)

  • "Estrutura de todo o BD para uma comunidade de usuários, com foco em entidades, tipos de dados, relacionamentos, operações e restrições" = nível CONCEITUAL. Não é o interno.
  • "Interno → armazenamento físico; externo → como os usuários veem; conceitual → todo o conteúdo de informações" = CERTO.

Cascas de banana CESPE

  • ErradoNo nível conceitual, cada esquema externo descreve a parte que interessa a um grupo…Mistura os níveis: isso é o nível externo
  • ErradoO esquema do nível externo oculta o físico e descreve entidades, tipos de dados…Essa é a descrição do conceitual
  • CertoNa arquitetura de três esquemas, o nível externo apresenta uma série de visões do usuárioExterno = visões
  • CertoNo nível interno são descritos os caminhos de acessoInterno = físico
  • ErradoOs níveis são interno, intermediário e externoO do meio é o conceitual
  • ErradoTodos os grupos usam o mesmo esquema externoHá um esquema externo por grupo
  • ErradoEsquemas dividem fisicamente as tabelas, evitando acesso cruzadoEsquema é descrição, não divisão física
  • ErradoVisões exibem aos aplicativos as alterações feitas no esquema conceitualVisões escondem essas alterações (independência)

Erro seu (Q50, item 53)

"Para definir e manter os dados é necessário o uso de sistemas de aplicação, o que caracteriza a dependência de dados, um fundamento do BD" → ERRADO. O fundamento é a INdependência dados-programa: o catálogo isola a definição dos dados dos programas.
  • Independência de dados ↔ abstração ↔ catálogo (a estrutura fica no catálogo, separada dos programas). Esse é o "isolamento entre programas e dados" de Navathe.
  • Q26 C: os dados não dependem do esquema físico e não precisam ser reescritos se ele for alterado.
  • Q16 E: alterar o nível interno não exige revisar o conceitual.
  • Q43: "modificar a definição de um nível sem afetar o nível superior" = independência de dados.
  • Pegadinha clássica: trocar a definição de lógica pela de física (TJ-CE, alternativa E).

Alta incidência · base de muitas questões C/E

Lembrete

Navathe: 3 propriedades implícitas do BD

  1. Representa um aspecto do mundo real: minimundo ou UoD (universo de discurso)
  2. Coleção logicamente coerente, com significado inerente (dados aleatórios não formam um BD)
  3. Construído para uma finalidade específica, com usuários e aplicações definidos

Definições por autor

  • Date: equivalente eletrônico de um armário de arquivamento
  • Heuser: dados integrados para uma comunidade de usuários
  • Silberschatz: dados estruturados, confiáveis, coerentes e compartilhados

Funções do SGBD × funções do sistema operacional

São do SGBD
Controle de acesso e segurança; integridade; controle de concorrência; transações; backup e recuperação; catálogo; otimização de consultas; DDL/DML; múltiplas visões; transformar e apresentar dados; controle multiusuário; interfaces de comunicação
NÃO são do SGBD (são do SO)
Escalonamento de processos na CPU; gerenciar o sistema de arquivos; gerenciar E/S de dispositivos; gerenciar a memória do computador
  • Q24 C: o objetivo do SGBD é retirar da aplicação cliente a responsabilidade de gerenciar acesso, persistência, manipulação e organização.
  • Q33 C: o DBA atribui as permissões, mas quem gerencia o acesso é o SGBD.
  • Q49 [69] E: os dados físicos não são acessados diretamente sem o SGBD.
  • Q36 E: BD "organizado de forma randômica, sem significado implícito" está errado (contraria Navathe).
  • Q50 [51] E: o BD trata multimídia sim (tipo BLOB).
  • Q7 C: um SGBD multiprocesso atende cada conexão com um processo do SO. No multithreading, são threads dentro do mesmo processo.

Navathe: 4 características da abordagem de BD (contra arquivos)

  • CaracterísticaSignifica
  • Natureza autodescritiva→O BD contém os dados e a sua descrição no catálogo (metadados)
  • Isolamento programas × dados + abstração→Gera a independência dados-programa
  • Suporte a múltiplas visões→Cada usuário vê uma parte; as visões podem ter dados virtuais/derivados (ex.: idade)
  • Compartilhamento + transações multiusuário→Exige controle de concorrência e ACID

Compartilhamento · redução da redundância · evita inconsistência · suporte a transações · integridade · segurança · balanceia requisitos conflitantes · padrões

Seus erros neste tema

  • Q6: "Autenticidade, consistência, isolamento e durabilidade" → E. O A é de Atomicidade. Leia cada palavra da sigla.
  • Q29: o funcionamento do BD baseia-se em unidades lógicas de trabalho = transações. Não são tabelas (tabela é estrutura; registro/ocorrência é linha; entidade é do MER).
  • Troca falsa comumCorreto
  • Autenticidade · Assincronia · Amorfabilidade · Automação→Atomicidade

  • Distributividade · Distribuição→Durabilidade

  • Q8 C: a atomicidade é chave para manter os dados precisos e em conformidade com as regras (gabarito Certo).

  • Controle de concorrência: vários podem ler, mas só um escreve o mesmo dado de cada vez ("só existe uma caneta").

As duas questões que você errou, lado a lado

  • CertoQ30: o SGBD realiza o controle da redundância, o que impede inconsistências entre os arquivos
  • ErradoQ2: o SGBD resolve problemas de integridade para evitar que a mesma informação fique duplicada em vários locais
Regra: controlar a redundância evita inconsistência. Integridade é consistência e precisão garantidas por restrições (PK, FK, UNIQUE, NOT NULL) definidas pelo projetista; o objetivo dela não é evitar duplicação. Não troque um conceito pelo outro.
  • Q40 E: "evitar a redundância controlada… cada informação armazenada uma única vez". A redundância controlada pode existir.
  • Q38 E: redundância "controlada pelo usuário" não é controlada.
  • Q50 [52] E: arquivos não têm "inter-relacionamento sem redundância". Essa é justamente a diferença deles para o BD.
  • Duas motos com a mesma placa → problema de redundância.

Erro seu (Q22)

"Nos BDs hierárquicos, cada registro é uma coleção de atributos, e a associação entre dois registros se chama ligação" → CERTO. Registro = coleção de atributos; associação = ligação (link) pai-filho. Q35 C: hierarquia ou árvore cujos nós contêm ocorrências de registros.

Problemas dos modelos hierárquico e de rede

  • Ponteiros de baixo nível
  • Armazenamento dependente do tipo de dado
  • Adicionar um campo exige reescrever o esquema físico
  • O usuário precisa conhecer a estrutura física

Os 4 tipos de NoSQL

  • Chave-valor: hash distribuído (Redis, DynamoDB)
  • Documento: sem esquema, bom para semiestruturado (MongoDB)
  • Colunar: grava por coluna, bom para OLAP (HBase, BigTable)
  • Grafo: nós, arestas e propriedades (Neo4j)
  • NoSQL não quer substituir o relacional; quer acabar com a ideia de "bala de prata".
  • Big Data = 5 Vs: volume, variedade, velocidade, veracidade, valor. Hadoop/MapReduce para processar.
  • Escalabilidade: horizontal = mais máquinas (sharding, motivo do NoSQL) × vertical = máquina mais potente.
  • E: "NoSQL usa modelos de armazenamento totalmente distintos dos relacionais".
